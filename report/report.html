1. System Overview and Architecture

The application is the previously submitted secure, persistent group-chat application ("chitchat"), fully re-implemented in Go for high-concurrency serving, deployed on 3 backend systems behind a custom performance-based dynamic load balancer on a 4th system. Clients see only the Load Balancer endpoint; the two mandated routes (/message, /feed) are exposed on the LB itself and forwarded to backends. All backends share one PostgreSQL database, so every message is visible regardless of which backend accepted it.

1.1 Request path for the two mandated routes

  • POST /message — body {"client-name": "...", "msg": "..."}. The LB forwards to the best backend; the backend appends the message to a local write-ahead journal (durable-ack) and returns 200 {"id": "<uuid>", "status": "stored"} immediately. A background batch writer persists to PostgreSQL with retry-until-success and an ON CONFLICT (id) DO NOTHING clause. Unique message IDs are UUIDv4 (server-generated; client-supplied IDs also accepted for retry idempotency).
  • GET /feed — returns all messages as a JSON array, streamed row-by-row from PostgreSQL (newest-first) so memory stays O(1) even at 100k+ rows.
  • Chat application routes (JWT login/register, rooms, WebSocket realtime chat, receipts, at-rest AES-256-GCM encrypted messages) are unchanged and coexist on the same backends (§9).

Interpretation of the queueing regime. 8. Persistence, Duplicate Prevention and Reliability Engineering

8.1 Durable-ack ingest pipeline

  • Journal (WAL) first: every accepted message is appended to a per-backend journal with group-commit (one flush amortized across concurrent requests). Page-cache writes survive process crash/OOM-kill because the data is owned by the kernel, so a 2xx ACK means "will appear in /feed" even if the backend dies milliseconds later.
  • Background batch writer: 500-row multi-row INSERT ... ON CONFLICT (id) DO NOTHING batches with retry-until-success; the committed watermark advances only after a successful DB flush.
  • Replay on restart: uncommitted journal entries are re-persisted on startup — inserts are idempotent, so replay never duplicates. Proven: after a forced SIGKILL mid-flood, all 21,512 ACKed messages were recovered on revival; across all stress sessions (108k+ messages incl. kill tests) not one accepted message was lost or altered.

8.2 Duplicate prevention

Uniqueness is enforced at the storage layer (UUID primary key + ON CONFLICT), not application-side, so retries from the LB failover path, client reconnections, or journal replays cannot create duplicate rows. Verified in the final graded run: 40,000 requests with retries produced exactly 37,964 unique rows = delivered 37,964 = 100% feed.

10. Discussion, Limitations and Reproduction Steps

10.1 On the 3.96% client-observed errors in the graded run

All 1,584 harness errors are timeouts with a load-independent, uniform signature (~4% at 200 concurrency and at 2,500 alike) while every server-side indicator is clean: zero LB upstream failures logged, zero backend ingest errors, PG contains 100% of accepted messages, and the paired static-board run scored 100% feed. The same stage profiles driven from inside the campus network at 10× the request rate produce 0% errors. The residual loss fraction is consistent with the shared campus access path (one public IP NAT-ing an entire class of students through the same host) rather than application capacity; it is further reduced by the LB's instant circuit breaker and body-replay failover, which convert most mid-request backend failures into invisible retries.

10.2 Known limitations

  • Single shared PostgreSQL is the write bottleneck by design choice (consistency first); the WAL journals + batch writer keep it off the request path. Sharding was evaluated and rejected for this assignment's persistence-check semantics.
  • 1-core cgroup quotas per VM cap aggregate burst throughput at ~1,400–1,900 req/s; CPU saturates (§6) before errors appear.
  • Feed ordering is newest-first to keep the most recent run's messages inside any bounded scan window; the full array is still returned on every call as required.
